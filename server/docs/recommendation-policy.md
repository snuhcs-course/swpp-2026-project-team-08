# 추천 정책

목차: [범위](#범위) · [구현과 요구사항](#구현과-요구사항) · [입력](#r1--진입과-입력-데이터)

- 추천은 보호자가 확인한 기록을 근거로 작은 변화 하나를 제안한다.
- 필수 제한과 충돌하거나 안전성을 확인할 수 없는 후보는 제공하지 않는다.
- 아래 정책은 요구사항이며 현재 구현 완료를 뜻하지 않는다.

## 범위

이 문서는 추천의 입력·안전성·근거·재사용 정책의 기준이다.
화면의 카드 조작·저장·시도 기록은 [추천 화면 명세](../../client/specs/suggestion/spec.md)를 따른다.
기존 클라이언트 정책 명세의 화면 전용 설명과 프로토타입 한계는 여기서 다루지 않는다.

## 구현과 요구사항

현재 [`validation.py`](../app/features/suggestions/validation.py)는 요청 음식의 누락·중복,
필수 문구, 재료 목록, 알 수 없는 재료와 제한 충돌을 검사한다.
[`workflow/prompts.py`](../app/features/suggestions/workflow/prompts.py)는 허용 재료 조회와
음식별 제안 하나 생성을 지시한다. 현재 사용자 프롬프트는 음식 ID와 이름을 전달한다.

프로필·식후 결과 전체를 활용한 근거 검증, 조리·제품별 불확실성 판단,
저장된 제안의 안전성 재검증은 위 두 파일의 검사만으로 충족 여부를 보장할 수 없다.
정책 적용 검증은 생성·저장·조회 경로를 함께 확인한다.

## R1 — 진입과 입력 데이터

1. 식후 검토 직후 진입하는 경우 해당 Meal ID를 사용해 데이터 조회 함수에서 최신 Meal과 확정된 식후 결과를 읽어야 한다. 화면 간에는 Meal이나 아동 프로필 전체 대신 필요한 식별자만 경로 매개변수로 전달한다.
2. 추천에는 보호자가 확인한 프로필의 알레르기·기타 필수 식이 제한, Safe Food의 조리·제공 형태, 감각 경향, 확인된 Meal 음식·재료·제공 형태, 식후 음식·재료별 결과와 선택적 어려움 기록을 사용할 수 있어야 한다.
3. 보호자가 확인하지 않은 사진 인식·비교 결과는 사실로 취급하지 않는다. 보호자 확정 값과 AI 추정이 충돌하면 보호자 확정 값을 우선한다.
4. 온보딩의 새로운 음식에 대한 일반적 친숙도는 추천의 참고 정보로만 사용한다.
5. 결과가 `Unclear`이거나 어려움 기록을 건너뛰었다면 해당 사실을 성공·실패 또는 특정 어려움으로 바꿔 해석하지 않는다.

## R2 — 필수 안전성 확인

1. 후보의 재료와 조리·제공 방식은 아동의 알레르기 및 기타 필수 식이 제한과 대조해야 한다. 제한과 충돌하는 후보는 표시하거나 저장할 수 없다.
2. 재료, 알레르기 정보 또는 필수 제한 준수 여부를 확인할 수 없는 음식 후보는 추천하지 않는다. 후보가 모두 제외되면 안전성을 확인할 수 없어 제안을 보류했다는 상태를 보여준다.
3. Safe Food 기록은 해당 음식의 기록된 조리·제공 형태에 관한 정보다. 이름이 같다는 이유만으로 다른 재료·조리·제공 형태의 안전성이나 수용 여부를 보장하지 않는다.
4. 감각 경향과 과거 반응은 적합성 판단을 돕는 정보로 사용하되 진단, 섭취 보장, 의학적 조언으로 표현하지 않는다. 보호자가 식품 표시와 교차 접촉 가능성을 직접 확인해야 한다는 안내를 제공한다.
5. 추천이 만들어진 뒤 프로필의 필수 제한이나 후보의 재료 정보가 바뀌면 저장·표시 전에 현재 데이터로 안전성을 다시 확인해야 한다. 기존에 저장된 제안도 재표시 또는 재사용 시 충돌 여부를 확인하고, 충돌하거나 확인할 수 없으면 시도 가능한 제안으로 노출하지 않는다.

## R3 — 제안 내용과 근거

1. 한 카드의 `WHAT TO TRY`에는 다음 식사에서 시도할 수 있는 음식, 조리 또는 제공 방식의 작은 변화 하나를 구체적으로 적는다. 한 카드에서 여러 독립적인 변화를 동시에 요구하지 않는다.
2. `WHY THIS MAY BE EASIER`에는 실제로 확인된 프로필 또는 식사 기록 중 해당 제안과 관련된 근거를 설명한다. 기록에 없는 반응이나 어려움을 만들어 이유로 쓰지 않는다.
3. `SERVING TIP`에는 제안을 어떻게 제공할지 이해할 수 있는 간결한 팁을 적는다. 팁은 R2의 제한과 모순되거나 카드의 한 가지 변화를 추가 과제로 확장해서는 안 된다.
4. 같은 음식이라도 재료·조리·제공 형태가 다르면 별도 food form으로 다룬다. 이전에 받아들인 형태의 기록을 다른 형태에 그대로 적용하지 않는다.
5. 기록이 부족하여 개인화 이유를 설명할 수 없다면 추측성 이유를 만들지 않는다. 안전하지만 개인화 근거가 없는 일반 제안을 `RECOMMENDED` 개인화 카드로 표시하지 않는다.
6. 카드에는 `RECOMMENDED` 출처를 표시하고, AI가 생성한 내용은 보호자가 선택하기 전까지 제안 상태로 유지한다.

## R5 — 추천 불가·로딩·오류 상태

1. 데이터를 읽거나 추천을 요청하는 동안 진행 상태를 표시한다. 취소하거나 화면을 떠난 뒤 도착한 오래된 응답은 최신 카드 상태를 덮어쓰지 않는다.
2. 필수 안전 정보를 확인할 수 없는 상태, 안전 후보가 없는 상태, 개인화 근거가 부족한 상태, 요청 자체가 실패한 상태를 구분한다. 어떤 경우에도 예시 카드나 검증되지 않은 후보를 성공 결과로 채우지 않는다.
3. 안전 정보가 부족하거나 서로 충돌하면 보호자가 관련 프로필·음식 정보를 확인할 수 있는 경로를 제공한다. 네트워크·서버 오류에는 현재 입력과 저장된 제안을 유지한 채 재시도 경로를 제공한다.
4. 제공 가능한 카드가 없더라도 식후 검토의 저장 완료를 취소하거나 결과 기록을 잃지 않는다.

## R6 — 저장된 제안과 식후 검토 연결

1. 저장된 제안은 제안 ID, 대상 아동, 근거가 된 Meal 또는 기록, 제안 내용, 저장 상태를 구분할 수 있어야 한다. UI에 표시할 한글·영어 문구는 앱 설정에 맞춰 제공하고, 저장된 식별자와 상태 값은 화면 언어와 분리한다.
2. Home의 Recommended action goals에는 실제 저장된 제안이 있을 때만 해당 제안과 `Try` 진입 동작을 연결한다. 저장된 제안이 없으면 디자인 예시를 실제 목표처럼 표시하지 않는다.
3. After-meal Review는 제안 사용 여부 확인 단계를 표시하지 않는다. 저장 또는 음식 연결만으로 시도 결과를 생성하지 않으며 기존 명시적 응답은 호환성을 위해 보존한다. C의 [최종 저장 요구사항](../../client/specs/after-meal-review/spec.md)을 따른다.
4. 프로필이나 음식 기록이 변경되어 저장된 제안의 근거 또는 안전성이 더 이상 성립하지 않으면 최신 정보에 맞게 상태를 갱신해야 한다. 과거의 선택·시도 기록은 지우지 않고, 현재 시도 가능한 제안과 구분한다.
