# Personalized Recommendation

## Goal

보호자가 확인한 아동 프로필과 식사·식후 기록을 바탕으로 다음 식사에서 시도할 수 있는 작은 변화 하나를 제안한다. 제안은 시도할 일, 그 이유, 제공 팁을 이해할 수 있게 보여주며, 보호자가 저장하거나 넘길 수 있다. 알레르기와 필수 식이 제한의 안전성을 확인할 수 없으면 음식 제안을 제공하지 않는다. 최종 음식 선택과 판단은 보호자가 한다.

## Design Document

현재 Figma에서 D. Personalized Recommendation의 독립 화면은 확인되지 않는다. 이 명세의 화면 근거는 C. After-meal Review의 [Recommended next step](https://www.figma.com/design/mxsRk3PMmZGuNpJVeAiRi5/NurtureBites?node-id=79-223) 카드와 [Did you try a saved suggestion?](https://www.figma.com/design/mxsRk3PMmZGuNpJVeAiRi5/NurtureBites?node-id=79-3), Home의 [Recommended action goals 위젯](https://www.figma.com/design/mxsRk3PMmZGuNpJVeAiRi5/NurtureBites?node-id=37-3369)이다. 카드·버튼·Home 위젯의 공통 시각 규칙은 [`specs/ui-components/spec.md`](../ui-components/spec.md)를 따른다. 별도의 Ideas 화면 구성, 카드 수, 추천 정렬 기준의 상세 디자인은 이 Figma 근거만으로 확정하지 않는다.

## User Flow

1. 보호자가 식후 검토를 마치거나 저장된 추천 진입점에서 제안을 확인한다.
2. 앱은 최신 아동 프로필, 보호자가 확인한 음식 정보와 식후 결과, 음식별 경험 기록을 불러온다.
3. 필수 안전 정보를 확인하고, 기록으로 설명할 수 있는 작은 변화의 후보를 검토한다.
4. 제공 가능한 후보가 있으면 보호자는 카드에서 시도할 일, 이유, 제공 팁을 읽는다.
5. 보호자는 제안을 저장하거나 넘긴다. 뒤로 이동해도 이미 저장한 선택은 유지된다.
6. 저장한 제안은 Home의 추천 목표 진입점과 이후 After-meal Review의 실행 여부 확인에서 다시 사용된다.

## Requirements

### R1 — 진입과 입력 데이터

1. 식후 검토 직후 진입하는 경우 해당 Meal ID를 사용해 데이터 조회 함수에서 최신 Meal과 확정된 식후 결과를 읽어야 한다. 화면 간에는 Meal이나 아동 프로필 전체 대신 필요한 식별자만 경로 매개변수로 전달한다.
2. 추천에는 보호자가 확인한 프로필의 알레르기·기타 필수 식이 제한, Safe Food의 조리·제공 형태, 감각 경향, 확인된 Meal 음식·재료·제공 형태, 식후 음식·재료별 결과와 선택적 어려움 기록을 사용할 수 있어야 한다. 해당 음식의 경험 단계가 실제로 기록되어 있다면 이를 사용할 수 있다.
3. 보호자가 확인하지 않은 사진 인식·비교 결과는 사실로 취급하지 않는다. 보호자 확정 값과 AI 추정이 충돌하면 보호자 확정 값을 우선한다.
4. 온보딩의 새로운 음식에 대한 일반적 친숙도는 개별 음식의 Exposure 단계를 확정하는 근거가 될 수 없다. 음식별 경험 단계가 없으면 없는 상태로 처리한다.
5. 결과가 `Unclear`이거나 어려움 기록을 건너뛰었다면 해당 사실을 성공·실패 또는 특정 어려움으로 바꿔 해석하지 않는다.

### R2 — 필수 안전성 확인

1. 후보의 재료와 조리·제공 방식은 아동의 알레르기 및 기타 필수 식이 제한과 대조해야 한다. 제한과 충돌하는 후보는 표시하거나 저장할 수 없다.
2. 재료, 알레르기 정보 또는 필수 제한 준수 여부를 확인할 수 없는 음식 후보는 추천하지 않는다. 후보가 모두 제외되면 안전성을 확인할 수 없어 제안을 보류했다는 상태를 보여준다.
   현재 로컬 프로토타입에는 재료별 제한 검증 목록이 없으므로, 알레르기 또는 기타 필수 식이 제한이 등록된 프로필의 음식 제안은 보류한다. 제한이 없음을 명시했고 재료를 확인한 기존 음식에 대해서만 제공 방식의 작은 변화를 제안한다.
3. Safe Food 기록은 해당 음식의 기록된 조리·제공 형태에 관한 정보다. 이름이 같다는 이유만으로 다른 재료·조리·제공 형태의 안전성이나 수용 여부를 보장하지 않는다.
4. 감각 경향과 과거 반응은 적합성 판단을 돕는 정보로 사용하되 진단, 섭취 보장, 의학적 조언으로 표현하지 않는다. 보호자가 식품 표시와 교차 접촉 가능성을 직접 확인해야 한다는 안내를 제공한다.
5. 추천이 만들어진 뒤 프로필의 필수 제한이나 후보의 재료 정보가 바뀌면 저장·표시 전에 현재 데이터로 안전성을 다시 확인해야 한다. 기존에 저장된 제안도 재표시 또는 재사용 시 충돌 여부를 확인하고, 충돌하거나 확인할 수 없으면 시도 가능한 제안으로 노출하지 않는다.

### R3 — 제안 내용과 근거

1. 한 카드의 `WHAT TO TRY`에는 다음 식사에서 시도할 수 있는 음식, 조리 또는 제공 방식의 작은 변화 하나를 구체적으로 적는다. 한 카드에서 여러 독립적인 변화를 동시에 요구하지 않는다.
2. `WHY THIS MAY BE EASIER`에는 실제로 확인된 프로필 또는 식사 기록 중 해당 제안과 관련된 근거를 설명한다. 기록에 없는 반응이나 어려움을 만들어 이유로 쓰지 않는다.
3. `SERVING TIP`에는 제안을 어떻게 제공할지 이해할 수 있는 간결한 팁을 적는다. 팁은 R2의 제한과 모순되거나 카드의 한 가지 변화를 추가 과제로 확장해서는 안 된다.
4. 같은 음식이라도 재료·조리·제공 형태가 다르면 별도 food form으로 다룬다. 이전에 받아들인 형태의 기록을 다른 형태에 그대로 적용하지 않는다.
5. 기록이 부족하여 개인화 이유를 설명할 수 없다면 추측성 이유를 만들지 않는다. 안전하지만 개인화 근거가 없는 일반 제안을 `RECOMMENDED` 개인화 카드로 표시하지 않는다.
6. 카드에는 `RECOMMENDED` 출처를 표시하고, AI가 생성한 내용은 보호자가 선택하기 전까지 제안 상태로 유지한다.

### R4 — 추천 카드와 선택

1. 사용 가능한 제안이 있으면 Figma의 `Recommended next step`처럼 카드 덱에 실제 후보만 표시한다. 카드에는 `WHAT TO TRY`, `WHY THIS MAY BE EASIER`, `SERVING TIP`이 모두 있어야 한다. 디자인 예시의 채소·밥과 같은 내용은 고정하지 않는다.
2. `✓` 또는 오른쪽 스와이프는 해당 제안을 저장하고, `×` 또는 왼쪽 스와이프는 해당 제안을 넘긴다. 두 입력 방식은 같은 결과를 내야 하며 한 번의 조작으로 한 카드만 처리한다.
3. 저장 성공 후 해당 제안은 저장된 제안으로 구분되어 이후 Home 진입점과 After-meal Review의 실행 여부 확인에 연결된다. 넘긴 제안은 저장된 제안으로 표시하지 않는다.
4. 뒤로 가기와 `Go back`은 이전 화면으로 돌아가며 이미 저장된 선택을 취소하지 않는다. 처리하지 않은 카드는 저장한 것으로 간주하지 않는다.
5. 저장 중에는 중복 입력으로 같은 제안이 여러 번 저장되지 않아야 한다. 저장이 실패하면 현재 카드와 선택을 유지하고 오류 및 재시도 경로를 제공한다.

### R5 — 추천 불가·로딩·오류 상태

1. 데이터를 읽거나 추천을 요청하는 동안 진행 상태를 표시한다. 취소하거나 화면을 떠난 뒤 도착한 오래된 응답은 최신 카드 상태를 덮어쓰지 않는다.
2. 필수 안전 정보를 확인할 수 없는 상태, 안전 후보가 없는 상태, 개인화 근거가 부족한 상태, 요청 자체가 실패한 상태를 구분한다. 어떤 경우에도 예시 카드나 검증되지 않은 후보를 성공 결과로 채우지 않는다.
3. 안전 정보가 부족하거나 서로 충돌하면 보호자가 관련 프로필·음식 정보를 확인할 수 있는 경로를 제공한다. 네트워크·서버 오류에는 현재 입력과 저장된 제안을 유지한 채 재시도 경로를 제공한다.
4. 제공 가능한 카드가 없더라도 식후 검토의 저장 완료를 취소하거나 결과 기록을 잃지 않는다.

### R6 — 저장된 제안과 식후 검토 연결

1. 저장된 제안은 제안 ID, 대상 아동, 근거가 된 Meal 또는 기록, 제안 내용, 저장 상태를 구분할 수 있어야 한다. UI에 표시할 한글·영어 문구는 앱 설정에 맞춰 제공하고, 저장된 식별자와 상태 값은 화면 언어와 분리한다.
2. Home의 Recommended action goals에는 실제 저장된 제안이 있을 때만 해당 제안과 `Try` 진입 동작을 연결한다. 저장된 제안이 없으면 디자인 예시를 실제 목표처럼 표시하지 않는다.
3. 이후 After-meal Review는 저장된 제안만 가져와 보호자가 시도했는지 묻는다. 추천 화면에서 저장했다는 사실과 실제로 시도했다는 결과는 별도로 기록한다. C의 [제안 후속 요구사항](../after-meal-review/spec.md)을 따른다.
4. 프로필이나 음식 기록이 변경되어 저장된 제안의 근거 또는 안전성이 더 이상 성립하지 않으면 최신 정보에 맞게 상태를 갱신해야 한다. 과거의 선택·시도 기록은 지우지 않고, 현재 시도 가능한 제안과 구분한다.

### R7 — 앱 구조와 문구

1. 화면 상태는 TypeScript 타입으로 정의한다. 데이터 로드·안전 확인·저장·재시도는 Screen, Feature Hook, `data/queries`와 `data/api`의 책임에 따라 처리한다. UI 컴포넌트는 데이터 접근 코드를 직접 호출하지 않는다.
2. 데이터 접근 함수는 추천에 필요한 모델과 성공·실패 결과를 Feature Hook에 제공한다. 추천 서비스가 없는 프로토타입에서 `data/api`에 mock을 사용하더라도 안전성·근거·저장 상태 규칙은 동일하게 적용한다.
3. 카드 제목, 설명, 안전 안내, 빈 상태, 오류, 버튼 등 앱의 모든 텍스트는 한글·영어를 한 파일에서 관리하고 앱 언어 설정에 따라 표시한다. 반복 색상은 공통 색상 파일에서 관리한다.
4. 카드의 저장·넘기기 동작은 색만으로 구분하지 않고 아이콘·접근성 설명을 함께 제공한다. 작은 화면에서도 이유와 팁을 읽고 두 동작에 접근할 수 있어야 한다.

## Edge Cases

- 알레르기 또는 필수 제한이 미입력·불확실·서로 충돌함
- 후보의 재료·조리 방식이 불명확하거나 기존 제한과 충돌함
- 이름은 같은 음식이지만 Safe Food와 조리·제공 형태가 다름
- AI 사진 분석은 음식을 제안했지만 보호자가 확인하지 않음
- 식후 결과가 `Unclear`이거나 선택적 어려움 기록을 Skip함
- 기록이 적어 개인화 이유를 설명할 수 없음
- 안전 후보가 없거나 후보가 모두 필터링됨
- 추천 로딩 중 Meal 또는 프로필이 수정되거나 화면을 이탈함
- 카드를 스와이프와 버튼으로 거의 동시에 처리함
- 저장 실패 후 재시도하거나 처리하지 않은 카드에서 뒤로 감
- 저장된 제안 이후 알레르기·제한 또는 음식 재료가 바뀜
- 저장된 제안은 있으나 아직 실제 시도 여부를 기록하지 않음

## Acceptance Criteria

Given 보호자가 Meal의 식후 결과를 확정했고<br>
When 해당 Meal에서 다음 제안을 열면<br>
Then 최신 프로필과 해당 Meal의 보호자 확인 데이터를 사용해 추천 상태를 표시한다.

Given AI 사진 비교가 음식 결과를 제안했지만 보호자가 확인하지 않았고<br>
When 추천 근거를 구성하면<br>
Then 그 제안을 확정된 식후 결과로 사용하지 않는다.

Given 후보 음식에 아동의 알레르기 또는 필수 식이 제한과 충돌하는 재료가 있고<br>
When 후보를 확인하면<br>
Then 그 후보는 추천 카드나 저장 가능한 제안으로 표시되지 않는다.

Given 후보의 재료 또는 필수 제한 준수 여부를 확인할 수 없고<br>
When 추천을 요청하면<br>
Then 해당 음식의 제안을 보류하고 확인이 필요한 정보를 안내한다.

Given Safe Food와 이름이 같지만 다른 조리·제공 형태의 후보가 있고<br>
When 근거를 평가하면<br>
Then Safe Food 기록만으로 그 후보의 안전성이나 수용 여부를 확정하지 않는다.

Given 보호자가 확인한 식후 어려움과 프로필의 제공 선호가 있고<br>
When 유효한 제안을 보여주면<br>
Then 한 가지 작은 변화와 실제 기록에 연결된 이유, 제공 팁을 카드에 표시한다.

Given 개인화 이유를 뒷받침할 기록이 없고<br>
When 제안을 요청하면<br>
Then 기록에 없는 이유를 만들지 않고 근거 부족 상태를 표시한다.

Given 추천 카드가 표시되고<br>
When 보호자가 `✓` 또는 오른쪽 스와이프를 사용하면<br>
Then 해당 제안이 한 번 저장되고 이후 저장된 제안 진입점에 표시된다.

Given 추천 카드가 표시되고<br>
When 보호자가 `×` 또는 왼쪽 스와이프를 사용하면<br>
Then 해당 카드는 넘어가며 저장된 제안에 포함되지 않는다.

Given 제안 저장 중 오류가 발생했고<br>
When 오류 상태를 확인하면<br>
Then 현재 카드와 선택이 유지되며 재시도할 수 있다.
