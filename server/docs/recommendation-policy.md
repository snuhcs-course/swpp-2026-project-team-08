# 추천 정책

목차: [범위](#범위) · [생성 입력과 검증](#생성-입력과-검증) · [입력](#r1--입력-데이터)

- 보호자가 홈 화면에서 요청하면, 아이가 편식하지 않을 가능성이 높은 음식을 한 장씩 추천한다.
  추천을 저장하거나 거절한 뒤 다시 요청하면 새 추천 한 장을 만든다.
- 보호자가 기록한 어려움 이유는 사실이 아니라 추정된 가설로 다룬다.
- 필수 제한과 충돌하거나 안전성을 확인할 수 없는 후보는 제공하지 않는다.

## 범위

이 문서는 추천의 입력·안전성·근거·재사용 정책의 기준이다.
화면의 카드 조작·저장·시도 기록은 [추천 화면 명세](../../client/specs/suggestion/spec.md)를 따른다.

## 생성 입력과 검증

[`workflow/prompts.py`](../app/features/suggestions/workflow/prompts.py)는 요청한 개수(홈 화면은 한 장)의
음식 추천 생성을 지시한다. 추천 하나는 음식 이름(`what_to_try`), 도움이 될 것이라 본 이유(`why_this_may_help`),
재료 목록(`ingredients`), 편식을 덜기 위한 제공 시 고려 사항(`preparation_method`)으로 이루어진다.
사용자 프롬프트는 다음을 전달한다.

- 아이의 연령대(프로필의 `age_group`).
- 편식 성향 가설: 최근 식후 리뷰에서 `EATEN`이 아닌 음식의 결과(`outcome`)와 어려워한 이유
  (`difficulty_reasons`), 따로 리뷰한 재료의 결과와 이유. 같은 이름의 음식은 최근 것 하나만 쓴다.
- 아이가 잘 먹는다고 기록된 음식([`familiar.py`](../app/features/suggestions/familiar.py)):
  과거 식사에서 `EATEN`으로 리뷰된 음식(최근 것부터, 같은 이름은 한 번만). 추천을 익숙한 것과 잇는
  근거로만 쓰며, 이 음식의 재료라도 쓸 수 있는 재료 목록에 없으면 추천에 쓰지 않는다.
- 보호자가 온보딩에서 기록한 거부 음식·조리 방법·거부 이유([`familiar.py`](../app/features/suggestions/familiar.py)).
  거부 이유는 어려움 이유와 같이 추정된 가설로 다루며, 기록된 형태의 참고 정보로 사용하고 알레르기나
  영구적인 금지로 취급하지 않는다.
- 지금까지 추천한 음식과 그 상태. 보호자가 이유를 골라 거절한 추천은 제외 이유를 함께 전달한다.
- 아이가 쓸 수 있는 재료 목록.

[`validation.py`](../app/features/suggestions/validation.py)는 추천 개수, 필수 문구, 재료 목록,
알 수 없는 재료, 같은 응답 안이나 지금까지의 추천과 겹치는 음식 이름을 검사한다.
검증을 통과한 추천은 가드레일([`guardrail.py`](../app/features/suggestions/workflow/guardrail.py))이
판정 모델에 보내, 추천의 재료마다와 추천 문장 전체가 아이의 알레르기·식이 제한에 어긋날 확률을 확인한다.
확률이 임계값 이상이면 다시 쓰게 하고, 재시도를 다 쓰거나 판정 호출이 실패하면 추천을 만들지 않는다.
판정은 확률적이므로 재료 카탈로그 검사를 대체하지 않고 더한다.

## R1 — 입력 데이터

1. 보호자는 홈 화면에서 원할 때 추천을 요청한다. 요청은 특정 식사나 음식을 가리키지 않으며, 서버는 요청한 사용자의 최신 프로필과 기록을 직접 읽는다. 클라이언트가 보낸 프로필이나 기록 값은 추천 입력으로 쓰지 않는다.
2. 추천에는 보호자가 확인한 프로필의 알레르기·기타 필수 식이 제한, 연령대, 온보딩에서 기록한 거부 음식과 그 조리 방법·거부 이유, 식후 음식·재료별 결과와 선택적 어려움 기록, 지금까지의 추천과 보호자의 결정(거절한 추천의 제외 이유 포함)을 사용한다.
3. 보호자가 확인하지 않은 사진 인식·비교 결과는 사실로 취급하지 않는다. 보호자 확정 값과 AI 추정이 충돌하면 보호자 확정 값을 우선한다.
4. (ToDo) 온보딩의 새로운 음식에 대한 일반적 친숙도는 추천의 참고 정보로만 사용한다. 현재 프로필은 이 값을 저장하지 않으므로 추천 입력에 없다.
5. (ToDo) 온보딩의 감각 프로필(아이가 민감하게 거부하는 식감 `sensory_textures`와 그 밖의 감각 특성 메모 `sensory_note`)은 아이의 편식 성향에 대한 보호자의 추정으로 추천에 사용한다. 현재 프로필은 이 값을 저장하지만 추천 입력에는 아직 넣지 않는다.
6. 보호자가 기록한 어려움 이유는 아이의 편식 성향에 대한 추정된 가설이다. 이유를 사실로 단정하지 않으며, 여러 기록에서 반복되는 이유를 하나의 기록에만 있는 이유보다 강한 근거로 본다.
7. 결과가 `Unclear`이거나 어려움 기록을 건너뛰었다면 해당 사실을 성공·실패 또는 특정 어려움으로 바꿔 해석하지 않는다.
8. 별도로 기록한 재료의 결과는 그 재료에 관한 근거이며, 음식 자체의 결과를 바꾸지 않는다.
9. 연령대는 그 나이의 아이가 먹기에 알맞은 음식·식감·크기를 고르는 데 사용한다.

## R2 — 필수 안전성 확인

1. 후보의 재료와 제공 시 고려 사항(`preparation_method`)은 아동의 알레르기 및 기타 필수 식이 제한과 대조해야 한다. 제한과 충돌하는 후보는 표시하거나 저장할 수 없다.
2. 재료, 알레르기 정보 또는 필수 제한 준수 여부를 확인할 수 없는 음식 후보는 추천하지 않는다. 후보가 모두 제외되면 안전성을 확인할 수 없어 제안을 보류했다는 상태를 보여준다.
3. 편식 성향 가설과 과거 반응은 적합성 판단을 돕는 정보로 사용하되 진단, 섭취 보장, 의학적 조언으로 표현하지 않는다. 보호자가 식품 표시와 교차 접촉 가능성을 직접 확인해야 한다는 안내를 제공한다.
4. 추천이 만들어진 뒤 프로필의 필수 제한이나 후보의 재료 정보가 바뀌면 저장·표시 전에 현재 데이터로 안전성을 다시 확인해야 한다. 기존에 저장된 제안도 재표시 또는 재사용 시 충돌 여부를 확인하고, 충돌하거나 확인할 수 없으면 시도 가능한 제안으로 노출하지 않는다.
5. 추천은 보호자가 다음 식사의 선택을 검토하는 데 사용한다. 최종 음식 선택과 판단은 보호자가 한다.

## R3 — 제안 내용과 근거

1. 한 카드의 `what_to_try`에는 아이에게 시도해 볼 음식 하나의 이름을 적는다. 한 카드에 여러 음식을 담지 않는다.
2. `why_this_may_help`에는 실제로 확인된 프로필 또는 식사 기록 중 해당 음식과 관련된 근거를 설명한다. 어려움 이유는 가설이므로 단정하지 않는 표현으로 쓰며, 기록에 없는 반응이나 어려움을 만들어 이유로 쓰지 않는다.
3. `ingredients`에는 추천한 음식에 들어가는 재료를 아이가 쓸 수 있는 재료 목록의 이름으로 빠짐없이 적는다.
4. `preparation_method`에는 편식을 덜기 위해 이 음식을 제공할 때 고려할 조리·손질·크기·제공 방식을 간결하게 적는다. R2의 제한과 모순되거나 여러 추가 과제로 확장해서는 안 된다.
5. 같은 음식이라도 재료·조리·제공 형태가 다르면 별도 food form으로 다룬다. 이전에 받아들인 형태의 기록을 다른 형태에 그대로 적용하지 않는다.
6. 식사 기록이나 거부 음식 기록이 없어도 연령대와 필수 제한만으로 추천할 수 있다. 이때 `why_this_may_help`는 연령대·제한에 근거해 설명하며, 기록이 없는 개인화 이유를 추측해 만들지 않는다.
7. 카드에는 `RECOMMENDED` 출처를 표시하고, AI가 생성한 내용은 보호자가 선택하기 전까지 제안 상태로 유지한다.

## R4 — 추천 불가·로딩·오류 상태

1. 데이터를 읽거나 추천을 요청하는 동안 진행 상태를 표시한다. 취소하거나 화면을 떠난 뒤 도착한 오래된 응답은 최신 카드 상태를 덮어쓰지 않는다.
2. 필수 안전 정보를 확인할 수 없는 상태, 안전 후보가 없는 상태, 요청 자체가 실패한 상태를 구분한다. 어떤 경우에도 예시 카드나 검증되지 않은 후보를 성공 결과로 채우지 않는다.
3. 안전 정보가 부족하거나 서로 충돌하면 보호자가 관련 프로필·음식 정보를 확인할 수 있는 경로를 제공한다. 네트워크·서버 오류에는 현재 입력과 저장된 제안을 유지한 채 재시도 경로를 제공한다.
4. 추천을 만들지 못하더라도 식사 기록과 이미 저장된 제안을 바꾸거나 잃지 않는다.

## R5 — 저장된 제안과 식후 검토 연결

1. 저장된 제안은 제안 ID, 대상 아동, 제안 내용, 저장 상태를 구분할 수 있어야 한다. 제안은 특정 Meal이나 음식에 묶이지 않는다. UI에 표시할 한글·영어 문구는 앱 설정에 맞춰 제공하고, 저장된 식별자와 상태 값은 화면 언어와 분리한다.
2. Home의 저장된 추천 진입점에는 실제 저장된 제안만 연결한다. 저장된 제안이 없으면 예시를 실제 추천으로 표시하지 않는다. 표시와 이동 동작은 [Home 명세](../../client/specs/home/spec.md)를 따른다.
3. After-meal Review는 제안 사용 여부 확인 단계를 표시하지 않는다. 저장 또는 음식 연결만으로 시도 결과를 생성하지 않으며 기존 명시적 응답은 호환성을 위해 보존한다. C의 [최종 저장 요구사항](../../client/specs/after-meal-review/spec.md)을 따른다.
4. 프로필이나 음식 기록이 변경되어 저장된 제안의 근거 또는 안전성이 더 이상 성립하지 않으면 최신 정보에 맞게 상태를 갱신해야 한다. 과거의 선택·시도 기록은 지우지 않고, 현재 시도 가능한 제안과 구분한다.

## R6 — 추천 이력과 거절

카드 전환·Undo는 [추천 화면 명세](../../client/specs/suggestion/spec.md)를 따른다.

1. 새 추천은 지금까지 추천한 음식과 같은 음식을 다시 추천하지 않는다. 이력에는 상태와 관계없이 모든 추천이 들어간다.
2. 거절 이유는 선택이며, 보호자는 이유를 고르지 않고 거절(Skip)할 수 있다. 보호자가 고른 제외 이유는 다음 생성 입력에 함께 전달한다. 제외 이유는 보호자의 판단이며, 아이의 식후 반응으로 바꾸거나 입력하지 않은 이유를 추측하지 않는다.
3. 한 번의 요청으로 추천 한 장을 만들고 새 ID로 저장한다. 기존 추천의 결정·제외 이유·저장·시도 기록은 바꾸지 않는다.
4. 생성·검증·저장 중 하나라도 실패하면 그 요청의 추천은 저장하지 않는다. 추천을 저장하거나 거절한 뒤의 재생성도 같은 요청이며, 보호자가 추천을 요청하는 횟수는 제한하지 않는다.
5. 기존 추가 생성 이력(`food_recommendation_retries`)은 보존하지만 새 추천 생성에는 쓰지 않는다.
